# Historical version-one metadata encoding and fixtures

Scope: B0/INT0 source at `038fe80f412754e5a7080240ca0e57ba3c19e368`, before D40's
removal of unused bridge/interop packages from active core. All file/type names
below describe that recorded revision. They are retained encoding evidence, not
current core interfaces or a requirement to re-create them. SEC2/INT0–INT3 are
`DEFERRED_UNTIL_EVE_TESTNET` for subsequently authorized separate programs.

All integers are checked. No floats, display rounding, time-dependent score,
network calls or transaction effects occur in this component. Source/destination
identity and recipient checks precede quotes; route admission still rejects every
B0 state even after metadata validation succeeds.

## Chain and address format

`ChainIdentity` binds namespace, 32-byte immutable genesis identity and a numeric
ID only for EVM namespaces. Numeric EVM chain IDs preserve the full U256 value;
zero IDs/genesis are invalid. Solana uses genesis with no EVM numeric ID.

Canonical identity bytes concatenate:

| Field | Encoding |
|---|---|
| Domain/version | ASCII `eve-chain-v1` followed by byte `00` |
| Namespace | One byte: EVE=1, Ethereum=2, Solana=3 |
| Genesis | Exactly 32 raw bytes |
| Numeric-ID presence | One byte: 0 absent, 1 present |
| Numeric ID | Exactly 32 big-endian bytes when present |

`ChainAddress` always carries this complete identity and either 20 EVM bytes or
32 Solana bytes. Raw decoding rejects any wrong width without truncation. EVM
machine display is exactly lower-case `0x` plus 40 hex characters; this is distinct
from a future wallet checksummed-display parser. Solana uses canonical base58 of
all 32 bytes. Display parsing has a byte-length cap before allocation and requires
re-encoding equality. Identical raw addresses on different genesis/namespaces are
different chain addresses.

## Asset and route binding

`AssetOrigin` is a network plus native kind, exact ERC-20 contract or exact SPL
mint/token-program addresses. Symbol names are not identity. Initial metadata
scope allows standard ERC-20 and the standard SPL token program only. Transfer-tax,
rebasing, callbacks, all Token-2022 assertions and unknown token programs fail.
A supplied Standard flag does not prove implementation behavior. Chain-specific
account/token inspection remains mandatory before any future custody approval.

`RouteManifest` is public unauthenticated metadata. Version-one immutable binding
bytes concatenate `eve-route-binding-v1` plus `00`, u16 big-endian version=1,
32-byte route ID, encoded source identity, destination identity, each custody
address (one-byte width then raw address), origin identity, asset kind tag
(native=0/ERC-20=1/SPL=2) and relevant raw contract/mint/program bytes, source and
destination decimal bytes, each maximum amount as 32-byte big-endian integer,
one-byte verifier requirement, and one-byte crypto-coverage disclosure.

Verifier requirement tags: Ethereum beacon finality/receipt=1, EVE consensus and
application commitment=2, Solana authenticated replay=3. Coverage tags:
CLASSICAL=1, HYBRID_EXPERIMENTAL=2, MIXED_TRUST=3. These are requirements/disclosures,
not successful authentication. B0 Solana replay is a conservative requirement;
a later authenticated-certificate profile needs a separate versioned identity.

State/discovery labels are mutable public metadata and excluded from the immutable
binding. None may approve execution. All existing states (not implemented, local
fixture, verifier incomplete, review required, paused) fail custody admission.
The future authenticated complete route manifest must additionally bind actual
implementation/verifier versions, historical profile/anchor policy, representations,
upgrade authority, exposure/delay/pause rules and evidence. This B0 encoding is
not a substitute for that completed custody manifest or economic transfer ID.

Amounts are positive native base-unit U256 values, with decimals 0–77 and a
checked power-of-ten factor. Downscaling rejects every remainder. Upscaling and
destination limits reject overflow; Solana metadata bounds are at most u64::MAX.
`TransferRequest` binds route ID, source amount and chain-scoped destination
recipient. Source and destination caps are both enforced. There is no dust refund,
timeout refund, wrapping execution or multi-route backing behavior.

## Frozen synthetic fixtures

`tests/fixtures/b0-binding-v1.json` contains explicit independent byte vectors
from this field table, not outputs generated by the Rust encoder during tests.
Fixture namespace/genesis pairs are deliberately synthetic: EVE=[01;32]/31337,
Ethereum=[02;32]/1 and Solana=[03;32]/no numeric ID. Custody byte patterns [04]/[05]
are test metadata, not deployed addresses. Four directional bindings preserve
native origin and convert 18/9 decimals exactly where required. No fixture claims
an actual external genesis, authenticated anchor, deployment or real asset.

Two-EVE SEC2 development fixture reservations are `eve-bridge-a-v1`/31337 with
synthetic genesis [a1;32] and `eve-bridge-b-v1`/31338 with [b2;32], fake 18-decimal
native `EVE_TEST` assets only, capped at 10^18 base units per metadata request.
`tests/fixtures/two-eve-reservations-v1.json` freezes these reservations and tests
reject custody admission. A future separate program would generate real independent
genesis files/hashes, enrolled sets, custody addresses and authenticated proofs
from actual EVE runtimes before executing SEC2. No reserved identifier may
be treated as a finality anchor or irreversible production-genesis choice.
